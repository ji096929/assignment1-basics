## 一、Unicode / 编码（unicode1、unicode2）

- `chr(0)` 是 `'\x00'`；它的 repr 和 print 显示不同（一个能看到转义形式，一个看不见）。
- 看不懂 `decode_utf8_bytes_to_str_wrong`：
  - `"".join(列表)` = 把列表里的字符串首尾相接（`join` 前面的 `""` 是分隔符）。
  - 执行顺序：Python 从最内层括号往外算；`for` 决定"哪一段要重复"。
  - 错在哪：UTF-8 是变长编码，一个字符可能占 2~4 字节。把字节拆开逐个解码，要么报
    `UnicodeDecodeError`（Python 3），要么得到乱码 `'Ã©'`（宽容解码器 / Python 2）。
  - 例子：`"é".encode("utf-8")` = `b'\xc3\xa9'`，逐字节解码会炸。
- `b'h'` vs `'h'`：前者是 bytes（元素是 0~255 的整数），后者是 str（元素是字符）。
- `bytes([b])` 为什么必须包一层：迭代 bytes 出来的是 int，而 `.decode()` 是 bytes 对象的方法。
- unicode2(c) 找非法两字节序列：文档没附规范表，要自己查规范或做实验。
  - 合法两字节的规则：首字节 `C2–DF`，第二字节 `80–BF`，缺一非法。
  - 例子：`b'\x80\x80'`（`0x80–0xBF` 是"跟随字节"，永远不能当序列开头）。

## 二、Python 语法（零基础）

- 类型标注（如 `dict[tuple[bytes, ...], int]`）只是**注释**，运行时不检查；读法是"从外往里剥"。
- 元组 = 把几个值捆成一个**不可变**的整体；不可变 → 可哈希 → 能当字典的键。
- `[...]` 用来建列表、**取下标**；`(...)` 用来调用函数、建元组。
- 缩进是语法：**冒号后面，下一行要多缩一级**。
- **定义函数 ≠ 调用函数**：`def` 只是给代码起名字，要另外写 `函数名()` 才会执行。
- `del` 会让后面的元素**整体前移**；边遍历边删时，下标要手动退一步。
- 跨目录 import 不用管目录：`from cs336_basics.tokenizer import ...`（包已经被 uv 装好了）。
- VSCode 解释器要手动指到 `.venv/bin/python`（工作区根目录不是项目根时，自动发现会失败）。

## 三、BPE 概念

- 每轮只挑**一对**合并，但这一对在**所有出现处**都合并。
- 第一轮参与合并的都是单字节；从第二轮起，成员可能是前面合并出来的多字节 token。
- 为什么要先统计词频：把语料压缩成 `{词: 次数}`。
  实测：22MB 文本 → 550 万次出现 → 只有 1.3 万种不同的词（压缩 420 倍）。
  不压缩的话，每轮 merge 都要扫全文，再乘上几千轮，完全不可行。
- 特殊 token：在 `train_bpe` 里只需"进词表、不参与合并"；它的语义（文档边界）是用分词器时才体现。
- `vocab` 只增不减：初始 256 个字节永远在里面，被合并掉的旧 token 也仍然保留。

## 四、环境（WSL / Windows）

- uv 只装在 Windows 侧，WSL 里找不到 → 另装 Linux 版 uv。
- PyPI 下载慢（约 0.6MB/s）→ 配清华镜像后约 7MB/s。（副作用：`uv.lock` 里的 source 被改写）
- 跑 `uv sync` 把 VSCode 卡死：WSL 只有 7.4G 内存，vscode-server 22 个进程占 3G，解压 torch 时打满 swap。
- GPU 不可用：驱动 572 只支持到 CUDA 12.8，而 torch 是 cu130 → 升级驱动到 580.97 后恢复。
- 实测算力（RTX 4050 Laptop 6GB）：bf16 GEMM **24.4 TFLOPS**；CPU 0.25 TFLOPS。差约 100 倍 → 训练一律用 GPU。

## 五、实现 train_bpe 踩的坑（基本都是报错教会的）

- **中文全角逗号 `，`** → SyntaxError，整个文件解析失败，IDE 的补全和自动缩进全部消失。
- `def` 少写冒号 → 同样症状。
- 函数定义完没有调用 → 跑完没有任何输出。
- `Counter(m.group())` 数的是字符串里的**字符**；正确做法：计数器建在循环**外**，循环里 `+= 1`。
- 替换时写 `i += 2`，跳过了本该检查的位置（因为 `del` 让元素前移），应为 `+= 1`。
- `vocab[...] = ...` 写在了"遍历所有词"的循环里 → 每轮其实只该加**一个**新 token。
- 报错读法（`assert` 类型）：`At index 26 diff: A != B` —— A 是我的输出、B 是参考；
  **前面全对说明逻辑是对的**，错误是累积出来的。

## 六、性能优化：增量更新

**问题**：朴素实现每轮重新扫描所有预分词、重建整张 pair 表，corpus.en 要跑 4.6 秒，测试要求 1.5 秒。

**profile 结论**：cProfile 显示时间几乎全在 `run_train_bpe` 自己的循环体里（`len()` 被调了 564 万次），不是库慢，是算法在重复劳动。

**思路**：维护 `pair → 含它的预分词集合` 的索引，每轮只处理"含 best_pair 的那些预分词"。
实测：4763 个预分词里只有 190 个受影响，**96% 是白扫的**。

**踩的坑**：
- `defaultdict()` 少了参数 → 访问缺键仍然 `KeyError`；要写 `defaultdict(set)`
- **遍历集合时修改它** → `RuntimeError: Set changed size during iteration`；
  遍历前先 `list(...)` 拍快照
- 加新 pair 时写成了 `counts[pair] += 新词频次` —— 新词此刻还没登记，`Counter` 返回 **0**
- 旧词没删、索引没拆 → `pretoken_freqs` / `counts` / `pair_on_pretoken` 三个结构不同步，结果一点点偏
- 用 `x -= x` 代替 `del`，留下 0 频次的幽灵条目

**概念澄清**：
- 统计**按出现次数**：`(a,a,a,b)` 里 `(a,a)` 出现 2 次 → 贡献 `2 × 频次`。
  实现上不需要手数次数，同一个 `zip` 循环会把重复的 pair 自动加/减多次。
- 合并影响的**不止 best_pair**，还有合并点左右两边的 pair：`(q,a),(a,a),(a,r)` → `(q,aa),(aa,r)`。
  "全扣全加"是保守但正确的做法（远处的 pair 扣了又加，净值为 0）。
- **统计用滑动窗口（重叠），替换不重叠**：统计是测量（每个相邻位置都算），
  替换是消费（一个 token 只能被一次合并吃掉）。
- 层级：文本 → 预分词（字符串）→ token 序列（元组）→ 相邻 pair（两个 token）。
  `word`/`pretoken` 在代码里指的是 **token 序列**，不是自然语言的"词"。

**结果**：`tests/test_train_bpe.py` 三条全过，总耗时 3.59 秒（含 5MB 语料的 special token 测试）。

## 七、TinyStories 训练：堆、并行与 2.1GB 实战

**profile 方法**：`uv run python -m cProfile -s tottime -o /tmp/prof.out 脚本`，再用
`pstats.Stats(...).print_stats(12)` 只看头部（全量输出几千行会把重点刷掉）。
`tottime` = 函数自身耗时，`cumtime` = 含子调用。先手动打点粗分阶段，再 cProfile 细看。

**堆优化（第二次提速：52s → 6.3s）**：profile 发现 90% 时间在 `max(counts, key=lambda)`——
每轮全扫 ~9600 个 pair × 9743 轮 = 1.46 亿次 lambda。换成 `heapq` 最小堆（O(n)→O(log n)）：
- 堆条目 `(-freq, pair)`：频次取负，"最大变最小"。
- **惰性删除**：pop 出的条目若频次与 `counts` 对不上（过期）就丢弃继续 pop；merge 后只把变化的 pair 重新压堆。
- **坑：并列方向反了**——最小堆在频次并列时弹字典序**最小**的，规则要**最大**。用包装类反转：
  `class RevPair: __lt__(self, other): return self.p > other.p`（魔术方法 `__lt__` 就是 `<` 本身）。
- **包装类的代价**：`counts.get(RevPair)` 永远查不到——没定义 `__hash__/__eq__` 时相等性按对象身份算。
  要么取值处 `.p` 拆包，要么给包装类补 `__hash__/__eq__` 委托。包装对象只在"比大小"场合有效。

**并行预分词（multiprocessing）**：主进程只传 `(path, start, end)` 坐标，worker 自己
`open("rb") → seek → read → decode`，返回本块的 Counter，主进程 `update` 合并。
- `find_chunk_boundaries`（物理切分，边界对齐特殊 token 开头）≠ `split`（语义切分，防跨 token 合并），两者配合；
- **进程间不共享内存**：传什么都要 pickle 拷贝。传 2.1GB 文本=拷贝 2.1GB；传两个整数≈免费 → 永远传坐标；
- worker 必须是模块顶层函数（pickle 限制）；`Pool` 放在 `if __name__ == "__main__":` 里；
- merge 循环**不能并行**（每轮依赖上一轮），merges 顺序天然正确——只并行预分词。

**并行部分的坑**：
- `pretokenization_example.py` 不能 import——顶层躺着占位示例代码（`open(...)`），import 即执行即炸。
  starter code 的正确用法是**把函数复制过来**（讲义允许 verbatim）；
- `open(..., "rb", encoding=...)` → `ValueError`：二进制模式没有编码概念；字节用
  `raw.decode("utf-8", errors="ignore")` 手动转（decode 是 bytes 的方法，不是 open 的参数）；
- **子进程的异常会打包传回主进程再抛出**（堆栈特征：`pool.starmap → raise self._value`）；
- 合并 Counter 时循环变量写错（把空索引加进词频表）→ 表空 → 堆空 → 循环 break →
  `return` 缩进在循环体内没执行 → 函数返回 None → 解包炸。

**swap 抖动（12 进程 vs 6 进程）**：12 个 worker（各 ~200MB）把 7.4G 的 WSL 顶满，
worker CPU 从 32% 掉到 10%、负载 0.17、单个 worker `read_bytes` 657MB（块只有 180MB，
多出来的全是换页搬运）——计算变成 RAM↔磁盘倒腾（差 1000 倍）。`Pool(6)` 后内存装得下，5.5 分钟跑完。
本机配置：Ryzen 5 6600H，6 物理核/12 逻辑核，WSL 默认拿全部逻辑核 + 内存一半。

**2.1GB 结果**：327s（冷缓存）→ 283s（热缓存，第二次读命中 page cache，基准测试要注明口径）。
- 内存测量陷阱：`RUSAGE_SELF` 只算主进程；`RUSAGE_CHILDREN` 是"已回收子进程的**最大**者"不是总和；
  准确的总峰值要用 psutil 后台线程定时采样 `self + children` 的 RSS；
- 最长 token：`b' accomplishment'`（及 disappointment / responsibility 一族）——
  TinyStories 高频完整词，合理；
- vocab/merges pickle 落盘仅 250KB（10000 词条）——后面"为什么 uint16 存 token id"的伏笔。

**writeup 素材对照**：(a) 时间 283s（热缓存）/内存（psutil 采样口径）/最长 token 及合理性；
(b) profile：优化前 90% 耗在 max → 堆 → 瓶颈转移到预分词 → 引出并行；
12 进程 vs 6 进程的 swap 抖动是现成的"并行度 ≠ 越多越快"观察。
